# How a Signal Becomes a Trade

Every automated trade on MetaStation — whether it arrives from a TradingView alert, a Telegram
channel, or your own script — travels the same path. Understanding it tells you exactly where to
look when a signal does not do what you expected.

```mermaid
graph TD
  A["Signal arrives: webhook POST or Telegram message"] --> B["Authenticate: the URL secret identifies the slot; the verification mode checks the sender"]
  B --> C["Parse: JSON or natural language"]
  C --> D{"Understood?"}
  D -- no --> R1["Rejected: parse error, nothing executed"]
  D -- yes --> E["Resolve size: percent, USD or token amount"]
  E --> F["Apply the slot's Trade Setting; refuse a stale opening signal"]
  F --> G{"Allowed?"}
  G -- no --> R2["Rejected: blocked by your own limits"]
  G -- yes --> H["Route to the slot's venue"]
  H --> I["Execute and attach take-profit and stop-loss"]
```

---

## 1. Arrival and authentication

A webhook signal is a `POST` to a URL that ends in a token unique to one slot:

```
https://metastation.fi/metastationapi/socialTrade/webhook/{your-webhook-secret}
```

**The secret in the URL identifies the slot.** There is no account field in the payload; routing
is entirely a function of which URL received the request.

What else a request must carry depends on the slot's **verification mode**:

| Mode | What is checked |
|---|---|
| **URL only** | Nothing else — anyone holding the URL can trade the slot |
| **Signed requests** | An `X-MetaStation-Signature` HMAC of the body with your signing key, within 300 seconds, used once |
| **Source-address check** | The request comes from TradingView's published addresses |

A Telegram signal is read from your own Telegram session in a channel you linked to the slot, and
delivered to the same webhook with the slot's secret — so it goes through the same pipeline.

→ [Secure Your Webhook](/docs/guides/secure-your-webhook)

## 2. Parsing

Two formats are accepted on the same endpoint, and the parser detects which one it is looking at.

**JSON** is explicit and unambiguous — the right choice for anything you generate yourself:

```json
{ "action": "open", "symbol": "BTCUSDC", "side": "buy", "quantity": "2%" }
```

**Natural language** is for signals written by humans, which is what Telegram channels and
hand-written TradingView alerts actually contain:

```
LONG BTC/USDT
Entry: Market
TP1: 48000
SL: 41000
```

From either form, the parser extracts action, symbol, direction, size, entry, take-profit levels,
stop loss and leverage.

:::note[It never guesses]
If a signal is ambiguous or missing a required field, MetaStation logs a parse error and executes
nothing. This is deliberate: a wrong trade is far more expensive than a missed one, and a parser
that fills in blanks would eventually fill one in wrongly with real money.
:::

→ [JSON Format](/docs/developer/json-format) · [Natural Language Format](/docs/developer/natural-language-format)

## 3. Size resolution

Size can be expressed three ways, and they behave differently as your balance changes:

| Form | Example | Resolves to |
|---|---|---|
| Percentage | `"2%"` | 2% of the slot's wallet balance **at the moment the signal arrives** |
| USD value | `"300 USD"` | $300 of notional. `"$300"` is not accepted |
| Token amount | `0.001` or `"0.001 BTC"` | Exactly that many tokens |

The percentage form is the one that surprises people: it compounds. A `2%` strategy takes larger
positions as the account grows and smaller ones as it shrinks, without any change to the alert.
A fixed USD amount does not.

## 4. Risk controls

Before anything is routed, the signal is checked against the slot's **Trade Setting** — a maximum
leverage (0–100×), a maximum percentage of balance and a maximum USD value — and its age:

- The caps **reduce** the signal rather than reject it: a slot capped at 5x executes a `20x` signal
  at 5x, and an oversized signal is cut to the cap
- A signal that names **no size** takes the slot's percentage or USD value as its size
- An **opening** signal more than **90 seconds** old is refused — measured from the signal's own
  `timestamp` when it sends one. A close is never refused for age
- The same request repeated within **60 seconds** runs once

Market filters and maximum open positions belong to **copy subscriptions**, not to a slot's own
signals. → [Copy Settings](/docs/social-trading/copy-settings)

→ [Risk Controls](/docs/concepts/risk-controls)

## 5. Routing and execution

The order is placed on whatever venue backs the slot — the on-chain order book for a MetaStation
Account, or Binance / ByBit / KuCoin through your API keys for a connected slot.

Take-profit levels and the stop loss in the signal are attached with the order. When the entry is a
resting limit order, they are placed **when it fills**, sized to the fill. If a stop cannot be
placed, the position is closed rather than left unprotected. SLX is set on the order ticket, not by
webhook.

→ [Order Execution](/docs/concepts/order-execution)

## When a signal does nothing

Work down this list in order — it matches the pipeline above, so the first failing step is the
answer:

| Check | Meaning |
|---|---|
| Did the sender get a `200`? | A `400` means the body was not understood; a `401`, the verification mode refused it; a `403`, the slot has no automation; a `404`, the URL is out of date |
| Does it appear in **History → Signal History**? | If not, it never arrived |
| Is it listed but not executed? | Its **Reason** says why — too old, no size, or refused by the exchange |
| Did it execute at the wrong size? | Check which size form the signal used, and the slot's Trade Setting caps |
